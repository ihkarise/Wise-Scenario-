B · Architecture in one picture
Design principles

Built as an engine, not a quiz

One engine, any number of cases

Stages, options, lives and scoring are all rows in the database. Case #1 and Case #5,000 go through the same code. There is no if (caseId === 1) anywhere.

The server keeps score

The browser never receives a correct answer or a future clue early. Lives are stored on the server, so refreshing the page cannot bring a life back.

Content and play kept apart

What authors write and what learners did live in separate tables, which keeps analytics clean.

Review before publish

Draft, review, publish, archive. Only Admins publish. Each published version is kept as a snapshot.

Phone first

Large tap targets, readable clues, installable as an app, keyboard and screen-reader friendly.

    BProposed architecture

    One Next.js application written in TypeScript and styled with Tailwind, hosted on Vercel. Supabase provides the PostgreSQL database, logins, file storage and Row Level Security. Components follow the shadcn/ui pattern used across 21st.dev, restyled in the WiseAitechs brand.

    • One app, clear folders. Cheap to host, easy to hand over, no microservices.
    • The server keeps score. Correct answers and future clues never reach the browser early.
    • One engine module runs the real player, the admin preview and the tests, so the game rules live in exactly one place.
    • Row Level Security is a second lock inside the database: drafts stay hidden even if a page has a bug.

    CDatabase design

    23 tables in six groups: People and access, Taxonomy, Content, Governance, Gameplay, Engagement. Content tables never store anything about a learner. Attempts point at a frozen published snapshot of the case. Optional homeopathy and repertory fields sit in a validated domain_fields column, so ordinary medical cases don't carry them. The Database tab has the full explorer.

    DCase engine design

    • Each case sets its own maximum lives and has any number of ordered stages.
    • Each stage has its own clue, question, interaction type and its own answer options (any count).
    • A wrong answer costs the stage's life cost (normally 1) and reveals the next stage. Earlier clues stay visible unless switched off.
    • A correct answer ends the case as a success, with a score from the central scoring rules.
    • Zero lives ends the case as failed and opens the full explanation.
    • Stages run out but lives remain: the learner stays on the last stage, the wrong option is struck out, and they try again. Authors can switch a case to "end immediately" instead.
    score = base × difficulty × clueEfficiency × lifeMultiplier clueEfficiency = 1 − 0.5 × (stageSolved − 1) / totalStages lifeMultiplier = 0.5 + 0.5 × livesLeft / maxLives

    EAdmin panel design

    1. Cases → New case. Fill in title, domain, category, difficulty and lives using plain form fields.
    2. Add stages. Type the clue, question and options; click Correct on the right answer. Move, duplicate or delete stages.
    3. Write the explanation, differentials and learning points. Homeopathy and repertory domains show their extra fields.
    4. Add references and tick each one as verified.
    5. The readiness panel lists anything missing in plain words, for example "Stage 3 has no correct answer."
    6. Autosave shows Saving…, Saved or Save failed.
    7. Preview as learner, submit for review, then an Admin publishes.

    FPlayer flow

    1. Open the case. The server checks it is published and starts an attempt, for a signed-in user or a guest.
    2. Read Stage 1, pick an option, submit.
    3. Wrong: one life is lost (shown with an icon and text), and the next clue appears with new options.
    4. Correct: the success screen shows the answer, clues used, lives left and score.
    5. Zero lives: the answer is revealed with the full explanation.
    6. Both endings lead to the reasoning review and a share card that never shows the answer.

    IDecisions that need you

    1
    Licence. Private and proprietary (recommended for a commercial product), or open source such as MIT? Case content lives in the database either way, not in the code.
    2
    Accounts. Who owns the Supabase and Vercel accounts? You create both (free tiers are enough to start) and add the keys through environment settings, never in chat or Git.
    3
    Google sign-in in the MVP? It needs a Google Cloud OAuth client under your organisation. Email and guest play work without it.
    4
    Who publishes at launch? Only you as Super Admin, or named reviewers? This sets how strict review is on day one.

    Everything else uses the defaults in this report: stay on the last stage when stages run out, previous clues stay visible, the answer is not revealed after a wrong guess, guests can play public cases, and English only to start (a language field is ready).
